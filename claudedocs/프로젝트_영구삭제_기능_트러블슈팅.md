# 프로젝트 영구삭제 기능 개선 - 트랜잭션 일관성과 N+1 문제 해결

## 🎯 배경

프로젝트 관리 시스템에서 **프로젝트 영구삭제(Hard Delete)** 기능과 **게시글 복원** 기능을 구현한 후, 코드 리뷰를 진행하던 중 여러 문제점들을 발견했습니다.

이번 포스팅에서는 발견된 문제들과 해결 과정을 단계별로 정리해보겠습니다.

## 🔍 1단계: 문제 분석

### 검토 대상 코드

**Controller (ProjectAdminController.java)**
```java
@DeleteMapping("/trash")
public CommonResponse<ProjectHardDeleteResponse> hardDeleteProject(
        HttpSession session,
        @Valid @RequestBody ProjectHardDeleteRequest request)
{
    Long loginUserId = SessionUtil.getLoginUserId(session);
    ProjectHardDeleteResponse response = projectService.hardDeleteProject(loginUserId, request);

    return CommonResponse.success("삭제된 프로젝트 영구삭제 성공", response);
}
```

**Service (ProjectServiceImpl.java)**
```java
@Override
@Transactional
public ProjectHardDeleteResponse hardDeleteProject(Long loginUserId, @Valid ProjectHardDeleteRequest request){
    // 1. 삭제 요청한 프로젝트 ID 목록 조회
    List<Long> projectIds = request.getProjectIds();
    List<Project> projects = projectRepository.findAllById(projectIds);

    // 2. 존재 개수 비교
    if (projects.size() != projectIds.size()) {
        throw new ProjectNotFoundException("존재하지 않는 프로젝트가 포함되어 있습니다.");
    }

    // 3. 삭제 여부 체크
    projects.forEach(project -> {
        if (!project.getIsDeleted()) {
            throw new BusinessException(ErrorCode.PROJECT_NOT_DELETED);
        }
    });

    // 4. S3 파일 삭제
    List<File> files = fileRepository.findByProjectIds(projectIds);
    fileService.deleteFilesFromS3(files);  // ⚠️ 문제!

    // 5. 프로젝트 삭제 (Cascade로 연관 엔티티도 삭제)
    projectRepository.deleteAll(projects);

    return ProjectHardDeleteResponse.Converter.from(projects);
}
```

**Request DTO (ProjectHardDeleteRequest.java)**
```java
@Getter
@NoArgsConstructor
@AllArgsConstructor
public class ProjectHardDeleteRequest {

    @JsonProperty("project_ids")
    private List<Long> projectIds;  // ⚠️ validation 없음
}
```

## 🚨 발견된 주요 문제점

### 1️⃣ Request Validation 부족

**문제점**
```java
@JsonProperty("project_ids")
private List<Long> projectIds;  // null이나 빈 리스트 허용
```

- `@NotNull`, `@NotEmpty` 등의 validation 어노테이션 부재
- null이나 빈 리스트 요청 시 처리 로직 없음
- 서비스 레이어에서 불필요한 검증 로직 필요

**영향**
- API 호출 시 명확한 에러 메시지 부재
- 잘못된 요청에 대한 조기 차단 불가

---

### 2️⃣ **트랜잭션 일관성 문제 (가장 심각!)**

**문제점**
```java
@Transactional
public ProjectHardDeleteResponse hardDeleteProject(...) {
    // ...

    // 4. S3 파일 삭제 (트랜잭션 내부)
    fileService.deleteFilesFromS3(files);

    // 5. DB 삭제
    projectRepository.deleteAll(projects);

    return ...;
}
```

**시나리오별 분석**

| 시나리오 | S3 삭제 | DB 삭제 | 결과 |
|---------|---------|---------|------|
| 정상 | ✅ 성공 | ✅ 성공 | ✅ 정상 |
| Case 1 | ✅ 성공 | ❌ 실패 | ⚠️ **S3만 삭제됨, DB는 롤백** |
| Case 2 | ❌ 실패 | - | ✅ 예외 발생, 트랜잭션 롤백 |

**Case 1의 문제**
- S3 파일은 이미 삭제됨 (AWS API 호출 완료)
- DB 삭제 실패로 트랜잭션 롤백
- **결과: DB에는 프로젝트 정보가 남아있지만, S3에는 파일이 없는 불일치 상태**

**왜 S3 삭제는 롤백 안 되나?**
- Spring `@Transactional`은 **DB 트랜잭션만** 관리
- S3 API 호출은 별도 외부 시스템 호출이라 롤백 불가능
- 트랜잭션 내에서 외부 API 호출은 위험!

### 3️⃣ 게시글 복원 기능의 N+1 문제

**PostServiceImpl.java - 문제 코드**
```java
@Transactional
public PostRestoreResponse restoreDeletedPost(Long loginUserId, PostRestoreRequest request){
    // ...
    List<Long> postIds = request.getPostIds();  // [1, 2, 3, ..., 100]
    List<Post> posts = postRepository.findAllById(postIds);  // 쿼리 1번

    // N+1 문제 발생!
    posts.forEach(post -> {
        post.restore();

        // 게시글마다 파일 조회 → 100번의 추가 쿼리!
        List<File> postFiles = fileRepository.findFilesByPostId(post.getPostId());
        for (File fileToRestore : postFiles) {
            fileToRestore.restore();
        }
    });

    postRepository.saveAll(posts);
    return PostRestoreResponse.Converter.from(posts, user.getId());
}
```

**문제 분석**
- 게시글 100개 복원 시 → **101번의 쿼리 실행** (게시글 1번 + 파일 100번)
- forEach 내부에서 `findFilesByPostId()` 반복 호출
- 대량 데이터 처리 시 성능 저하

**쿼리 실행 예시**
```sql
-- 쿼리 1: 게시글 조회
SELECT * FROM post WHERE post_id IN (1, 2, 3, ..., 100);

-- 쿼리 2~101: 각 게시글마다 파일 조회
SELECT * FROM file WHERE post_id = 1;
SELECT * FROM file WHERE post_id = 2;
SELECT * FROM file WHERE post_id = 3;
...
SELECT * FROM file WHERE post_id = 100;
```

### ✅ 해결 2: 트랜잭션 분리 (순서 변경)

**초기 시도: 트랜잭션 분리**

처음에는 DB 삭제를 별도 트랜잭션 메서드로 분리했습니다.

```java
@Override
public ProjectHardDeleteResponse hardDeleteProject(...) {
    // ...

    // DB 삭제 (별도 트랜잭션)
    hardDeleteProjectsInTransaction(projects);

    // S3 삭제 (트랜잭션 밖)
    fileService.deleteFilesFromS3(files);

    return ...;
}

@Transactional
private void hardDeleteProjectsInTransaction(List<Project> projects) {
    projectRepository.deleteAll(projects);
}
```

**❌ Self-invocation 문제 발생!**

IntelliJ에서 노란색 경고:
```
@Transactional 자동 호출(실질적으로 타깃 객체 내의 메서드가 타깃 객체 내의 다른 메서드를 호출)은
런타임 시 실제 트랜잭션을 발생시키지 않습니다
```

**Self-invocation이란?**
- 같은 클래스 내에서 `@Transactional` 메서드를 직접 호출
- Spring AOP 프록시를 거치지 않음
- 트랜잭션이 실제로 작동하지 않음!

```
Client → Proxy → Target Object
                    ↓
                 method1() → method2()  ← 프록시 우회!
```

**최종 해결: 순서 변경 + 단일 트랜잭션**

```java
@Override
@Transactional
public ProjectHardDeleteResponse hardDeleteProject(Long loginUserId, @Valid ProjectHardDeleteRequest request){

    // 1-3. 검증 로직
    List<Long> projectIds = request.getProjectIds();
    List<Project> projects = projectRepository.findAllById(projectIds);

    if (projects.size() != projectIds.size()) {
        throw new ProjectNotFoundException("존재하지 않는 프로젝트가 포함되어 있습니다.");
    }

    projects.forEach(project -> {
        if (!project.getIsDeleted()) {
            throw new BusinessException(ErrorCode.PROJECT_NOT_DELETED);
        }
    });

    // 4. S3에서 삭제할 파일 목록 조회
    List<File> files = fileRepository.findByProjectIds(projectIds);

    // 5. S3 파일 먼저 삭제 (실패 시 예외 발생 → 트랜잭션 롤백)
    fileService.deleteFilesFromS3(files);

    // 6. DB에서 프로젝트 삭제 (트랜잭션으로 보호, Cascade로 연관 엔티티도 삭제)
    projectRepository.deleteAll(projects);

    return ProjectHardDeleteResponse.Converter.from(projects);
}
```

**순서 변경 이유**

| 시나리오 | S3 삭제 | DB 삭제 | 최종 상태 | 복구 가능성 |
|---------|---------|---------|----------|-----------|
| **정상** | ✅ 성공 | ✅ 성공 | ✅ 완전 삭제 | - |
| **S3 실패** | ❌ 실패 | - | ✅ DB 유지 (롤백) | ✅ 재시도 가능 |
| **S3 성공 + DB 실패** | ✅ 성공 | ❌ 실패 | ⚠️ S3만 삭제, DB 유지 | ⚠️ 수동 정리 필요 |

**왜 이 순서가 더 안전한가?**
- **DB 기록이 남아있으면** → S3 파일 목록을 다시 찾아서 정리 가능
- **DB만 삭제되고 S3 남으면** → orphan 파일 영구 잔존 (찾기 어려움)

### ✅ 해결 3: N+1 문제 해결 - Bulk 조회

**수정된 코드 (PostServiceImpl.java)**

```java
@Transactional
public PostRestoreResponse restoreDeletedPost(Long loginUserId, PostRestoreRequest request){
    // ...
    List<Long> postIds = request.getPostIds();
    List<Post> posts = postRepository.findAllById(postIds);

    // 4. 삭제 여부 체크
    posts.forEach(post -> {
        if (!post.getIsDeleted()) {
            throw new BusinessException(ErrorCode.BOARD_NOT_DELETED);
        }
    });

    // 5. 모든 게시글의 파일을 한 번에 조회 (N+1 문제 해결!)
    List<File> allFiles = fileRepository.findByPostIds(postIds);
    Map<Long, List<File>> filesByPostId = allFiles.stream()
            .collect(Collectors.groupingBy(file -> file.getPost().getPostId()));

    // 6. 게시글과 파일 복원
    posts.forEach(post -> {
        post.restore();

        // Map에서 파일 조회 (추가 쿼리 없음)
        List<File> postFiles = filesByPostId.getOrDefault(post.getPostId(), List.of());
        postFiles.forEach(File::restore);
    });

    postRepository.saveAll(posts);
    return PostRestoreResponse.Converter.from(posts, user.getId());
}
```

**FileRepository에 추가된 메서드**
```java
@Query("select f from File f where f.post.postId in :postIds")
List<File> findByPostIds(List<Long> postIds);
```

**개선된 쿼리 실행**
```sql
-- 쿼리 1: 게시글 조회
SELECT * FROM post WHERE post_id IN (1, 2, 3, ..., 100);

-- 쿼리 2: 모든 파일 한 번에 조회 (끝!)
SELECT * FROM file WHERE post_id IN (1, 2, 3, ..., 100);
```

**핵심 개선 포인트**
1. **Bulk 조회**: `findByPostIds()`로 모든 파일을 1번의 쿼리로 조회
2. **Map으로 그룹핑**: `Collectors.groupingBy()`로 게시글 ID별 파일 분류
3. **메모리 조회**: forEach에서는 Map에서 파일을 꺼내기만 (DB 쿼리 없음)

## 🎓 배운 점

### 1. 외부 시스템과 트랜잭션

**핵심 원칙**
- Spring `@Transactional`은 **DB 트랜잭션만** 관리
- S3, 외부 API 호출은 트랜잭션 범위 밖
- 외부 시스템 호출은 가능한 트랜잭션 밖에서 실행

**2-Phase Commit의 한계**
- 분산 트랜잭션(XA) 구현 복잡도 높음
- 현실적으로 **순서 조정**과 **보상 트랜잭션**으로 해결

### 2. Self-invocation 문제

**Spring AOP의 동작 원리**
```java
// 외부에서 호출 (프록시 O)
projectService.hardDeleteProject(...);  // ✅ @Transactional 작동

// 같은 클래스 내부에서 호출 (프록시 X)
this.hardDeleteProjectsInTransaction(...);  // ❌ @Transactional 무시
```

**해결 방법**
1. **Self-injection**: 자신을 주입받아 프록시를 통해 호출
2. **별도 클래스 분리**: 트랜잭션 메서드를 다른 빈으로 분리
3. **메서드 병합**: 하나의 트랜잭션 메서드로 통합 (이번 선택)

### 3. N+1 문제 해결 패턴

**일반적인 해결 방법**
```java
// 1. Bulk 조회 (이번에 사용)
List<Entity> entities = repository.findByIds(ids);

// 2. JOIN FETCH (JPQL)
@Query("SELECT e FROM Entity e JOIN FETCH e.children WHERE e.id IN :ids")

// 3. @EntityGraph
@EntityGraph(attributePaths = {"children"})
List<Entity> findByIdIn(List<Long> ids);
```
