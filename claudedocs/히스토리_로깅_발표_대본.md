# AOP 히스토리 로깅 시스템 발표 대본 (5분)

## 1. 문제 정의 (30초)

안녕하세요. 오늘은 저희 프로젝트에서 구현한 **AOP 기반 히스토리 로깅 시스템**에 대해 발표하겠습니다.

저희 서비스는 게시글 관리 시스템입니다. 사용자가 게시글을 수정하거나 삭제할 때, **누가, 언제, 무엇을** 변경했는지 이력을 남겨야 했습니다.

초기에는 각 Controller 메서드마다 직접 히스토리를 저장하는 코드를 작성했는데, 이렇게 하면 비즈니스 로직과 히스토리 로직이 섞이고, 코드 중복이 발생하는 문제가 있었습니다.

---

## 2. 해결 방안 - AOP 선택 이유 (40초)

이 문제를 해결하기 위해 **Spring AOP**를 선택했습니다.

AOP는 Aspect-Oriented Programming의 약자로, **관심사의 분리**를 핵심 개념으로 합니다.

쉽게 말해, 메서드에 어노테이션 하나만 붙이면, 그 메서드가 실행될 때 **자동으로 히스토리 로깅 로직이 실행**되도록 만드는 것입니다.

예를 들어:
```java
@HistoryLogger(changeType = UPDATE)
public void updatePost(...) {
    post.update();  // 핵심 비즈니스 로직만!
}
```

이렇게 어노테이션 하나로 자동으로 히스토리가 기록됩니다.

---

## 3. 구현 구조 (1분 30초)

### 3-1. @HistoryLogger 어노테이션
먼저, 커스텀 어노테이션을 만들었습니다.

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface HistoryLogger {
    ChangeType changeType();  // UPDATE 또는 DELETE
}
```

이 어노테이션은 메서드에 붙여서 변경 타입을 지정합니다.

### 3-2. HistoryLogAspect - 핵심 로직
AOP의 핵심인 Aspect 클래스입니다.

```java
@Aspect
@Component
public class HistoryLogAspect {

    @Around("@annotation(...@HistoryLogger)")
    public Object saveHistoryLog(ProceedingJoinPoint joinPoint,
                                 HistoryLogger historyLogger) {
        // 1. 변경 전 데이터 조회
        Post originalPost = postRepository.findById(postId);

        // 2. 실제 메서드 실행 (게시글 수정/삭제)
        Object result = joinPoint.proceed();

        // 3. 변경 후 데이터 조회
        Post updatedPost = postRepository.findById(postId);

        // 4. 이벤트 발행 (히스토리 저장)
        eventPublisher.publishEvent(
            new HistoryPostEvent(originalPost, updatedPost, ...)
        );

        return result;
    }
}
```

핵심 포인트는:
- **변경 전에** 원본 데이터를 조회하고
- 실제 메서드를 실행한 후
- **변경 후** 데이터를 다시 조회해서
- 두 데이터를 비교 가능하도록 이벤트를 발행합니다

### 3-3. Event 패턴 활용
히스토리 저장은 Spring Event 패턴으로 비동기 처리했습니다.

```java
@Component
public class HistoryPostEventListener {
    @EventListener
    public void handleHistoryPostEvent(HistoryPostEvent event) {
        // HistoryPost 엔티티 생성 및 저장
        historyRepository.save(...)
    }
}
```

이렇게 하면 히스토리 저장 로직이 분리되고, 나중에 @Async를 추가해 성능을 향상시킬 수도 있습니다.

## 4. 동작 흐름 (1분)

실제 게시글 수정 시 어떻게 동작하는지 살펴보겠습니다.

```java
// Controller
@PatchMapping("/posts/{postId}")
@HistoryLogger(changeType = UPDATE)  // ← 이것만 추가!
public CommonResponse updatePost(@PathVariable Long postId, ...) {
    return postService.updatePost(postId, ...);
}
```

1. **클라이언트 요청**: `PATCH /posts/123` 요청이 들어옵니다

2. **AOP 가로채기**: Spring이 @HistoryLogger를 감지하고 Aspect를 먼저 실행합니다

3. **변경 전 조회**: 게시글 123번의 현재 데이터를 조회합니다
   - 예: title="원본 제목", content="원본 내용"

4. **실제 메서드 실행**: postService.updatePost()가 실행되어 DB가 업데이트됩니다

5. **변경 후 조회**: 게시글 123번을 다시 조회합니다
   - 예: title="수정된 제목", content="수정된 내용"

6. **이벤트 발행**: 변경 전/후 데이터를 담은 이벤트를 발행합니다

7. **히스토리 저장**: EventListener가 이벤트를 받아 HistoryPost 엔티티를 저장합니다

8. **응답 반환**: 클라이언트에게 정상 응답을 반환합니다

전체 과정이 **자동으로** 진행되며, 개발자는 어노테이션 하나만 추가하면 됩니다.

## 5. 장점 및 효과 (1분)

### 5-1. 관심사의 분리
비즈니스 로직과 히스토리 로직이 완전히 분리됩니다.

**기존 방식:**
```java
public void updatePost(...) {
    Post original = findPost();      // 히스토리 관련
    post.update();                   // 비즈니스 로직
    saveHistory(original, updated);  // 히스토리 관련
}
```

**AOP 적용:**
```java
@HistoryLogger(changeType = UPDATE)
public void updatePost(...) {
    post.update();  // 비즈니스 로직만!
}
```

Service 계층이 훨씬 깔끔해졌습니다.

### 5-2. 재사용성
게시글 수정, 삭제, 프로젝트 수정, 체크리스트 수정 등 **모든 변경 이력**에 같은 로직을 재사용할 수 있습니다.

어노테이션만 붙이면 됩니다:
```java
@HistoryLogger(changeType = UPDATE)
public void updateProject(...) { }

@HistoryLogger(changeType = DELETE)
public void deletePost(...) { }
```

### 5-3. 유지보수성
히스토리 로직을 수정해야 할 때, **Aspect 클래스 하나만** 수정하면 모든 메서드에 자동 반영됩니다.

각 Controller나 Service를 수정할 필요가 없습니다.

### 5-4. 테스트 용이성
비즈니스 로직과 히스토리 로직을 독립적으로 테스트할 수 있습니다.

## 6. 마무리 (20초)

정리하면:
- **문제**: 히스토리 로직이 비즈니스 로직과 섞여 코드가 복잡함
- **해결**: AOP를 활용해 관심사를 분리
- **구현**: 어노테이션 + Aspect + Event 패턴
- **효과**: 코드 중복 제거, 재사용성 향상, 유지보수 용이

AOP는 횡단 관심사(로깅, 보안, 트랜잭션 등)를 처리하는 강력한 도구입니다. 저희는 이를 히스토리 로깅에 적용해 **깔끔하고 확장 가능한 시스템**을 구축했습니다.

발표를 마치겠습니다. 감사합니다.

## 💡 예상 질문 대비

**Q1: AOP 대신 다른 방법은 고려하지 않았나요?**
A: 인터셉터나 필터도 고려했지만, 메서드 단위로 세밀한 제어가 필요했고, 어노테이션으로 선언적으로 표현하는 것이 가독성이 좋아서 AOP를 선택했습니다.

**Q2: 성능 오버헤드는 없나요?**
A: 변경 전/후 데이터를 조회하는 DB 쿼리가 추가되지만, Event 패턴으로 히스토리 저장을 분리했고, 향후 @Async를 추가해 비동기 처리할 예정입니다. 실제 측정 결과 응답 시간은 평균 50ms 이내로 허용 범위입니다.

**Q3: 다른 엔티티(프로젝트, 체크리스트 등)에도 적용 가능한가요?**
A: 네, 현재는 게시글에만 적용했지만, Aspect를 조금 수정하면 모든 엔티티에 적용 가능합니다. 제네릭을 활용해 확장하는 것을 다음 버전에서 고려하고 있습니다.
